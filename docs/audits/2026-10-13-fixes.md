# Inventory release fixes — 13 October 2026

## Implemented

- Updated vulnerable Python dependencies; local dependency audit reports no known vulnerabilities.
- CSV fields neutralize spreadsheet formula prefixes and escape quotes/newlines. Exports freeze the selected center, cancel on identity changes, and reject changed totals or duplicate records.
- Inventory filtering, pagination and dashboard counts run in database queries, without the previous catalogue row cap.
- Today's movement count uses each center's configured timezone, falling back to Asia/Kolkata for invalid timezone names.
- All active inventory memberships are resolved deterministically. Write permission is checked for the requested center, including mixed administrator/accountant assignments.
- Center-selector alignment corrected; application scripts and offline shell versioned for cache refresh.
- Session restoration starts after navigation initialization. Refreshing a screen invalidates stale asynchronous results.
- `/ready` probes Supabase authentication and the required reporting migration; `/health` remains a liveness check. Readiness responses are never cached by the service worker.

## Deployment order — required

1. Take a database backup and verify its restore on an isolated database. Keep the currently deployed application commit available for rollback.
2. Apply any outstanding migrations in filename order, ending with `supabase/migrations/202610130001_inventory_reporting.sql`. This migration validates existing finite-cost constraints; if it fails, investigate the historical values rather than silently replacing them.
3. Deploy this application revision to staging with its matching Supabase project URL and public key. Never use a service-role key in browser configuration.
4. Verify `/ready` returns HTTP 200 with `status: ready`. Existing manually configured Render services must have their health-check path changed to `/ready`; editing render.yaml alone does not update such services.
5. Use approved staging accounts to test a receipt, issue, return/correction, location transfer, refresh, logout and center isolation. Confirm physical quantities and audit entries agree. Automated browser checks use simulated API responses and do not replace this staging check.
6. Rotate previously shared database passwords and owner PIN through their supported administration flows, update server secrets, and revoke old sessions where appropriate. Do not publish credentials in source control.
7. After staging acceptance, deploy the same revision and migration to production and repeat the readiness/login check. If application rollback is needed, restore the previous application commit; the added read-only reporting functions can remain in place. Restore a database backup only through an approved data-recovery process.

## Scope and remaining limitations

- Transfers are between storage locations **within one center**; cross-center dispatch/receipt is not implemented.
- Reports provide stock CSV, not a full accounting/audit reporting suite.
- Paginated CSV export is not a transactionally frozen historical snapshot. Concurrent edits can change values between pages; use a quiet reporting window when reconciling stock.
- This local fix pass does not certify live database migration state, live account access, secret rotation, backup restoration or production deployment.
